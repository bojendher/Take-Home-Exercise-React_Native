  Server (server/, no dependencies, run with npm run server on port 4000):
  - How uploads work: the app creates a session, sends each photo one at a time,
    then finalises it. You can ask the server which photos it already has,
    which is how resuming works.
  - Retrying is always safe: re-sending the same photo number replaces it, and a
    repeated "create" request returns the original session.
  - Validation: the server checks the file's actual contents rather than the
    type the app claims. It enforces size and count limits (15 MB per photo, 50
    photos), and every error comes back with a clear code.
  - Failure simulation, controlled at runtime through /__sim:
    - Presets: off, slow, flaky, down.
    - Settings for latency, error rate, hangs and dropped connections.
    - A "lost response" mode: the server saves the photo but the app never hears
      back. This is the case that proves retries don't create duplicates.
    - A queue to force the outcome of the next few requests, so a failure can be
      reproduced exactly.
  - Address: in development the app finds the server automatically on the same
    machine that serves the app. Set EXPO_PUBLIC_API_URL to use a different
    address. This replaces the old EXPO_PUBLIC_UPLOAD_URL.

  documented as taking path segments, so passing one URI string is shown only by
  that example. The page does not describe the constructor's handling of
  `file://` strings directly.
  - `expo-image-picker` is not mentioned on this page. The documented pattern is
  the picker example above.

  **Sync vs async:** Methods with a `Sync` suffix are the synchronous versions.
  Methods without the suffix that the page lists as `Promise<...>` are async
  (`copy`, `move`, `write`, `text`, `bytes`, `base64`, `digest`, `preview`,
  `upload`). `create`, `delete`, `list`, `rename`, and `info` (File and
  Directory) are documented as returning `void`, `(File|Directory)[]`, or an
  info object, so they are synchronous. `copy`/`move` mutate the object
  differently, see below.

  **Throws:** Only the cases quoted above are documented. The page gives no
  general error contract.

  **Does `copy()` mutate the source uri?** Not documented. The copy example logs
  only `copiedFile.uri` after `file.copy(copiedFile)`. The move example is
  explicit: after `await file.move(Paths.cache)`, `file.uri` becomes
  `'${cacheDirectory}/example.txt'`. The page says `move` "Updates the `uri`
  property that now points to the new location." So `move` mutates the source
  object's `uri`. `copy` does not appear to, but the page does not state it.

  **Passing File to fetch/FormData:** Yes, documented, but using `fetch` from
  `'expo/fetch'`, not the global fetch:
  - `fetch(url, { method: 'POST', body: file })` with `file` a `File`.
  - `formData.append('data', file)`, then pass `formData` as body.
  - Also `file.upload(url, options)` and `file.createUploadTask(url, options)`.
  The page says `upload` "rejected only when the file cannot be read, the
  request fails, or the upload is cancelled. Non-2xx responses still resolve."
  - Download: `File.downloadFileAsync(url, destination)`, and `fetch` from
  `expo/fetch` with `src.write(await response.bytes())`.

  **Other notes:** `File.pickFileAsync()` is a static picker, Android-tested per
  the page's wording. `File.preview`/`canPreview` are Android/iOS only.
  `FileHandle` via `file.open(FileMode.ReadOnly)`. The legacy API is
  `expo-file-system/legacy`.

  ## 2. expo-sqlite (SDK 58 page)

  **Version and install:** "Recommended version: ~58.0.18". Install with `npx
  expo install expo-sqlite`.

  **Expo Go:** Yes. The page says "Included in Expo Go". SQLCipher is not
  supported in Expo Go.

  **Web:** Yes, the header lists `web`, along with android, ios, macos, tvos.
  - Requirements (verbatim): "To use `expo-sqlite` on web, you need to configure
  Metro bundler to support **wasm** files and add HTTP headers to allow
  `SharedArrayBuffer` usage."
  - Metro config (verbatim diff): `config.resolver.assetExts.push('wasm');` and
  `config.server.enhanceMiddleware` setting
  `res.setHeader('Cross-Origin-Embedder-Policy', 'credentialless');` and
  `res.setHeader('Cross-Origin-Opener-Policy', 'same-origin');`.
  - Deployment: the same COEP/COOP headers must be set on your web host. On Expo
  Hosting they go in the `expo-router` plugin `headers` config.
  - Optional custom WASM: `SQLite.configureWeb({ wasmURL:
  require('../assets/wa-sqlite-fts.wasm') })`, called before opening any
  database. The page says the config plugin options (`enableFTS`,
  `useSQLCipher`) only apply to Android and iOS, and that FTS is absent on web
  by default.
  - [SUMMARY] `withExclusiveTransactionAsync` and `interruptSync` are not
  supported on web.

  **Key-value store** (verbatim import and examples):
  - `import Storage from 'expo-sqlite/kv-store';`
  - `await Storage.setItem('key', JSON.stringify({ entity: 'value' }));`
  - `const value = await Storage.getItem('key');`
  - `Storage.setItemSync('key', 'value');` and `const value =
  Storage.getItemSync('key');`
  - The page says it's "a drop-in replacement for the
  `@react-native-async-storage/async-storage` library."
  - [SUMMARY] The reference section documents a class `SQLiteStorage`
  (constructor takes a database name) with
  `getItemAsync`/`setItemAsync`/`removeItemAsync`, sync
  `getItemSync`/`setItemSync`/`removeItemSync`, and aliases
  `getItem`/`setItem`/`removeItem`. The summary says `removeItem` is documented
  with conflicting return types (`Promise<void>` vs `Promise<boolean>`). I did
  not see `removeItem` verbatim, so treat it as unverified.
  - The reference also has constants `SQLite.AsyncStorage` and `SQLite.Storage`
  (aliases of `SQLiteStorage`).

  **Database API:**
  - `const db = await SQLite.openDatabaseAsync('databaseName');` (verbatim). The
  sync variant is `openDatabaseSync(databaseName, options, directory)`
  [SUMMARY, signature only, no example, and `directory` is not supported on
  web].
  - `execAsync(source)` returns `Promise<void>`. The page says "The queries are
  not escaped for you!" It is for multi-statement SQL: `await
  db.execAsync(\`PRAGMA journal_mode = WAL; CREATE TABLE ...\`);`. `execSync`
  exists.
  - `runAsync(source, params)` returns `Promise<SQLiteRunResult>` with `changes`
  and `lastInsertRowId`. Verbatim: `await db.runAsync('INSERT INTO test (value,
  intValue) VALUES (?, ?)', 'aaa', 100);`. It also accepts an array, or named
  parameters as an object (`{ $value: 'aaa' }`).
  - `getFirstAsync(source, params)` returns `Promise<T | null>` [SUMMARY for the
  exact type]. Verbatim use: `const firstRow = await db.getFirstAsync('SELECT *
  FROM test');`
  - `getAllAsync(source, params)` returns `Promise<T[]>`. Verbatim: `const
  allRows = await db.getAllAsync('SELECT * FROM test');` (the summary said this
  entry was missing, but it appears in the verbatim text). `getAllSync` also
  exists.
  - `getEachAsync` is an async iterator: `for await (const row of
  db.getEachAsync('SELECT * FROM test'))`.
  - `withTransactionAsync(task)`: verbatim example `await
  db.withTransactionAsync(async () => { ... });`. The page warns that "any query
  that runs while the transaction is active will be included in the
  transaction." It says `withExclusiveTransactionAsync` fixes this, but it runs
  on a new connection, so `PRAGMA foreign_keys = ON` does not apply inside it.
  [SUMMARY] the regular `withTransactionAsync` "is not exclusive and can be
  interrupted by other async queries."
  - Prepared statements: `db.prepareAsync(sql)` then
  `statement.executeAsync(params)` and `finalizeAsync()`.
  - Tagged template API: `db.sql` with `` sql`SELECT ... ${value}` ``,
  `.first()`, `.each()`, `.allSync()`, `.firstSync()`.
  - `SQLiteProvider` with `databaseName`, `onInit`, `useSuspense`, and
  `useSQLiteContext()` hook.

  Not documented on this page: a standalone `execAsync` entry (only in examples
  and the summary); a verbatim `openDatabaseSync` example; any statement on
  whether the expo-sqlite default-export `Storage` is the same object as
  `SQLite.Storage` (summary implies yes, but the page does not say so).
